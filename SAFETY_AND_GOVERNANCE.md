## 1. The Fundamental Industrial Safety Imperative

In strict accordance with Section 10 of the Master Instruction:
> **"Maintain a strict distinction between code-generation autonomy and operational control. Never independently deploy generated code to production PLCs or modify live industrial equipment. Never bypass emergency stops, safety interlocks, protective functions, safety-rated logic or other industrial protection mechanisms."**

Industrial automation controls high-voltage motors, multi-ton hydraulic stamping rams, 4500-ton die-casting injection cells, explosive chemical processes, high-speed robotic welding cells, and extreme thermal systems. A software defect or unauthorized memory write can cause catastrophic physical destruction, fires, toxic releases, severe physical injury, or loss of life.

Therefore, this platform enforces a strict, mathematical, and cryptographic **Safety Air-Gap** between the AI generation environment and physical plant equipment.

## 2. Inviolable Safety Restrictions

### 2.1 Absolute Prohibition on Autonomous Live Deployment
- **Zero Live Execution Autonomy**: The AI platform possesses **ZERO direct network capability to download firmware, initiate online edits, or force I/O bits on a running production PLC**.
- All network protocols supported by the Protocol Abstraction Layer (`lumina_pal.py`) for live connections (Siemens S7 Comm, Rockwell CIP, Modbus TCP, OPC UA) are strictly restricted to **read-only telemetry ingestion** during normal operations.
- The write socket is physically decoupled. Any candidate code or parameter patch generated by the AI is delivered strictly as a file artifact (`.L5X`, `.scl`, `.TcPOU`, `.st`) for manual review on an offline engineering workstation.

### 2.2 Inviolability of Safety Systems & Hardware Interlocks
- **IEC 61508 / IEC 62061 (SIL-2 / SIL-3) & ISO 13849-1 (PLd / PLe)**:
  - Standard automation code must never interfere with, bypass, or overwrite safety-rated signals.
  - In Rockwell GuardLogix, Siemens F-CPU, or Beckhoff TwinSAFE architectures, safety logic resides strictly within dedicated **Safety Tasks** and **Fail-Safe Blocks (F-Blocks)**.
  - The AI code generation engine is programmatically barred from writing to safety memory addresses or tags designated with `SAFETY_`, `ESTOP_`, `LIGHTCURTAIN_`, or `INTERLOCK_`.
- **Hardware Permissives**: Emergency stops, safety gate limit switches, and hydraulic over-pressure relief valves must remain **hardwired through safety relays or safety-rated contactors**. Software logic must never be treated as a substitute for physical hardwired safety interlocks.

### 2.3 Mandatory Truthfulness in Simulation & Compilation Reporting
In compliance with Section 9:
> **"Where a compiler or simulator is unavailable, explicitly report the limitation. Never claim code has been compiled, tested or simulated when it has not."**
- If an external compiler (e.g., Siemens TIA Portal Openness CLI or Rockwell Studio 5000 Logix Designer) is not connected to the test harness, the platform explicitly outputs:
  `[STATUS: SYNTAX VERIFIED VIA INTERNAL AST PARSER — COMPILATION ON HARDWARE VENDOR RUNTIME WAS NOT CONDUCTED]`.
- If a hardware-in-the-loop (HIL) testbench is not available, the platform explicitly reports:
  `[STATUS: VERIFIED VIA SOFTPLC SIMULATION TWIN — REAL-TIME HARDWARE DYNAMICS WERE NOT EXECUTED]`.

## 3. The 3-Tier Human Authorization Proxy

To ensure rigorous governance, the platform classifies all suggested code refactorings, parameter tunings, and diagnostics into three distinct **Risk Tiers** implemented in `lumina/backend/lumina_security.py`:

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│                              3-TIER GOVERNANCE PROXY                                   │
├────────────────────────────────────────────────────────────────────────────────────────┤
│ TIER 1: Non-Critical Telemetry Monitoring & Offline Code Export                        │
│ - Scope: Viewing telemetry, generating offline ST/SCL files, reviewing causal advice. │
│ - Authorization: Standard authenticated controls engineer session.                     │
│                                                                                        │
│ TIER 2: Simulated Sandbox Patching & Engineering Review                                │
│ - Scope: Applying test patches inside the SoftPLC Digital Twin sandbox.                │
│ - Authorization: Qualified Controls Engineer review with cryptographic signature.       │
│                                                                                        │
│ TIER 3: Safety-Critical Logic Modification & Hardware Staging                          │
│ - Scope: Any code modifying motion limits, hydraulic pressures, or cycle sequencing.  │
│ - Authorization: MANDATORY DUAL-ENGINEERING SIGN-OFF (M-of-N keyswitch attestation).   │
└────────────────────────────────────────────────────────────────────────────────────────┘
```

### 3.1 Dual Engineering Sign-Off Protocol (Tier 3)
Any candidate code export touching Tier 3 parameters requires:
1. **Primary Controls Engineer**: Reviews code diff, AST syntax audit, and Z3 SMT formal proof. Signs with cryptographic token.
2. **Independent Safety Auditor**: Verifies that emergency stops, mechanical limits, and pressure reliefs remain untouched. Signs with secondary token.
3. **Physical Hardware Permissive**: The target PLC must be placed in `PROGRAM` or `REMOTE RUN` mode via a physical mechanical keyswitch on the chassis door before any download can proceed via approved vendor tools.

## 4. Hardware Deployment Proxy & Golden Master Rollback

In laboratory, pilot, or staging environments where authorized testing takes place:
1. **Pre-Deployment Cryptographic Snapshot**:
   - Before any staged controller logic is exported, the `HardwareDeploymentProxy` captures a bit-exact **Golden Master Snapshot** of all controller tags, state vectors, and firmware routines, computing a SHA-256 integrity hash.
2. **Deterministic Golden Master Rollback**:
   - In the event of an unexpected fault, anomalous vibration spike ($>2.5g$), or operator abort during commissioning, the proxy executes a deterministic **sub-25ms Golden Master Rollback**:
     ```python
     # lumina/backend/lumina_security.py
     def execute_golden_rollback(target_cell: str) -> Dict[str, Any]:
         """Restores verified pre-test firmware and tag state in < 25ms."""
         ...
     ```
3. **Black-Box Flight Recorder**:
   - All interactions, user prompts, generated AST structures, verification gauntlet outputs, and engineering sign-offs are immutably logged to an append-only, tamper-evident audit ledger (`catalog/governance_audit.jsonl`).
